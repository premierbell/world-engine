## 핵심 컨셉

**사용자는 콘텐츠를 수집하는 것이 아니라, 자신의 세계를 성장시킨다.**
**AI는 이해하고, 알고리즘(과 V1부터는 최종적으로 사용자)이 결정한다.**

URL을 스크랩하면 → AI가 임베딩(의미 이해)을 만들고 → 결정론적 알고리즘이
바다 위에 섬(Island)으로 클러스터링·배치하고 → 스크랩이 쌓이며 섬이
성장하고 그 안에서 관심사가 갈라지면 섬 내부에 Topic(건물)이 생긴다.
"스크랩 정리 서비스"는 이 엔진 위에서 동작하는 첫 애플리케이션일 뿐 -
나중에 메모/PDF/유튜브/뉴스레터로 입력이 확장돼도 엔진 자체는 재사용
가능해야 한다는 관점("World Engine").

## 세계의 구조

```
바다 (미배정 스크랩이 떠 있는 공간)
 └── Island (관심사 하나, 예: "여행", "개발")
      └── Topic (Island 안의 하위 관심사, 예: "부산 해변", "면접")
           └── Scrap (실제로 저장한 글 하나)
```

- **Island는 정체성으로서 영속적이다.** `identity_vector`(생성 시점에
  고정, 절대 갱신 안 함)로 "이 스크랩이 이 섬에 속하는가"를 판단한다.
  `growth_vector`(EMA로 계속 갱신)는 "요즘 이 섬이 어느 방향으로
  움직이고 있는가"를 보여주는 참고 지표일 뿐, 편입 판단에는 절대 쓰지
  않는다. 이 둘의 코사인 유사도가 Identity Stability - 섬이 원래
  정체성에서 얼마나 멀어졌는지(drift)를 보여준다.
- **좌표(섬의 위치)는 계산 결과가 아니라 영속 상태다.** 새 섬은 가장
  가까운 기존 섬 옆에 로컬로 배치되고(Nearest Neighbor), 기존 섬은
  한 번 자리 잡으면 절대 움직이지 않는다. 비결정적 소스(random)는 배치
  로직에 쓰지 않는다.
- **Topic은 Island 내부에서 관심사가 갈라질 때 생긴다** - 스크랩
  개수가 일정 수를 넘어서가 아니라, 실제로 서로 다른 하위 클러스터가
  형성되는 시점에 생긴다(`Topic.center_vector`, EMA로 갱신).

## 성장 지표와 시각적 티어는 분리된 개념이다

- **Growth Point**(구현 완료, 2026-08-08): 내부 성장 수치. V0 Step 7
  때 계획만 되고 미뤄졌던 걸 V0가 예시로 든 "스크랩 수, 정정 이력 등"
  중 가장 단순한 `scrapCount`만으로 시작 - 정정 이력 등 다른 요소는
  필요 근거가 쌓이면 추가. DB에 저장하지 않고 매 요청마다 계산만 한다
  (`GrowthTier.fromScrapCount`, `island/model/`).
- **시각적 티어(Seed → Islet → Village → City)**(구현 완료, 2026-08-08):
  Growth Point를 사람이 보는 성장 단계로 매핑. 경계값 1~3/4~10/11~30/
  31+는 첫 실사용 데이터 분포를 보고 잡은 가안.
  - **지금(임시 중간 단계)**: 지도 라벨에 텍스트로 표시("여행 (23) ·
    Village"), 섬 원은 티어별로 같은 파란 계열의 명도만 다르게(연한
    하늘색 Seed → 진한 남색 City). **이건 최종 디자인이 아니다** -
    "일단 가장 단순한 방식으로 체감 가능하게 만들고, 실사용해보며
    다음 단계를 판단한다"는 이 프로젝트의 반복된 원칙을 그대로 적용.
  - **장기 목표(미착수, 별도 디자인 세션 필요)**: 스크랩이 쌓일수록
    섬 자체에 실제로 마을 → 도시가 자라나는 시각적 변화(아이콘/
    일러스트 수준)가 나타난다. 색상 체계도 그 설계 때 함께 다시
    정한다 - 지금의 파란 계열 명도 차이에 얽매이지 않는다.
- 건물(Topic)은 이 티어와 별개로, 클러스터 형성 시점에 생긴다.

## 제품 원칙 (6줄)

1. 사용자는 세계를 성장시킨다.
2. 세계는 안정적이어야 한다(정체성이 함부로 안 흔들림).
3. AI는 이해하고, 알고리즘은 결정한다.
4. 모든 성장은 체감 가능해야 한다.
5. 세계는 완성되지 않는다.
6. 비교와 경쟁은 목적이 아니다.

V1부터는 3번에 단서가 붙는다 - **AI 추천 + 사용자 확인**으로, "알고리즘이
전부 자동으로 결정한다"가 아니라 "AI는 이해까지, 최종 배치는 사용자가
확인한다"로 조정됨(아래 "왜 이렇게 바뀌었는가" 참고).

## 왜 이렇게 바뀌었는가 (V0 → V1)

V0 원안은 Topic까지 알고리즘이 완전 자동으로 재구성하는 걸 목표로
했다(`prototype/night_batch.py`의 Merge/Split/Union-Find/HDBSCAN
시도). `docs/algorithm_limitations.md` Finding #005/#006: 표본이 너무
적은 단위(Topic당 평균 3개 미만)에서 embedding noise가 그대로 드러나
전부 실패했다. **실패한 건 "Topic"이라는 개념이 아니라 "그 판단을 AI가
전부 대신하게 만드는 것"이었다** - 신호(Pairwise LLM Judgment) 자체는
Finding #012(AUC 0.82~0.94)로 이미 검증됨. 그래서 V1은 "AI 추천 →
사용자 확인" 구조로 설계를 바꿨고, V2(Topic 부활)도 같은 원칙을
따른다 - AI는 후보만 제안하고, 최종 확정(생성/merge)은 항상 사용자가
한다(`docs/v2_design.md`, `docs/v2_architecture_review.md` Finding A).

## 로드맵

- **V0 — Validation**(완료): Python 프로토타입으로 임베딩/threshold/
  클러스터링 가정을 전부 검증. 결론: 완전 자동 분류는 불가능.
- **V1 — Genesis**(완료): Java/Spring Boot로 Scrap Flow(추출→임베딩→
  Island 추천→사용자 확인) 전체 루프 완주.
- **V2 — Evolution**(진행 중, 지금 여기): Topic 부활(후보 생성→기존
  매칭→승인→편입→병렬화 완료), 성장 지표/시각적 티어/Topic 이름 AI
  제안은 아직. 지금은 로직 안정화 관찰 + 프런트를 React로 옮기는 작업
  병행 시작.
- **V3 — Memory**(미착수): 이름만 있고 상세 설계 없음 - 스크랩이 오래돼
  다시 안 보게 되는 것(폐허?) 등을 다룰 것으로 추정되나 확정 아님.
- **V4 — Exploration**(미착수): 이름만 있고 상세 설계 없음.

V3/V4는 이름 외에 확정된 내용이 없다 - 이 문서에 있는 이름만으로
설계를 추측하지 말고, 실제로 그 단계에 도달했을 때 다시 논의해서
채울 것.
