# Map-as-Home 화면 재설계 논의 (시작 2026-08-03)

## 상태

**지도 UI(패널/라우팅/줌/모바일) 구현 완료(PR #103, 2026-08-04
머지).** Nearest Neighbor 배치 알고리즘은 2026-08-05에 설계 완료,
**구현은 아직** - "Nearest Neighbor 배치 알고리즘" 섹션 참고.

## 왜 이 논의가 시작됐는가

Topic 목록 정렬(PR #102)까지 끝내고 나니 남은 후보가 두 개였다 -
① MapView 완성도(확대/축소, 애니메이션, 배치), ② 모바일 대응. 그런데
둘 다 "지금 화면을 어떻게 짤 것인가"라는 같은 질문에 걸려 있다는 게
드러남 - MapView는 Island 좌표가 실제로 의미를 가지면 화면을 얼마나
차지해야 하는지부터 정해야 하고, 모바일 대응도 지금의 데스크톱
2-컬럼(`main` + `sidebar`) 레이아웃을 그대로 좁힐 게 아니라 뭘
숨기고 뭘 보여줄지부터 정해야 함 - 결국 레이아웃 재설계 하나로
합쳐지는 문제.

## 사용자 활동을 두 모드로 나눔 (핵심 재프레이밍)

이유를 "지도가 커지니까"가 아니라 **사용자가 이 서비스에서 뭘
하는가**로 잡음:

- **탐험(Exploration)** - 대부분의 시간. `지도 → 섬 선택 → Topic
  탐색 → 스크랩 읽기`. 지도가 주인공.
- **수집(Capture)** - 짧게 끝나는 작업. `글 발견 → 스크랩 추가 →
  AI 추천 확인 → Topic 선택`.

이 구분이 "스크랩 추가는 상시 노출이어야 하는가, 필요할 때만
열면 되는가"를 가른다 - **후자로 결정**: 수집은 짧고 가끔 하는
작업이라 지도를 가릴 필요가 없다.

## 결정된 방향

1. **지도가 홈(Home)이다.** 앱을 열면 지도가 가장 먼저, 가장 크게
   보인다. 스크랩 추가/최근 스크랩/Island 목록은 전부 지도를
   보조하는 UI로 재배치된다.
2. **섬 클릭 시 페이지 전환이 아니라 확대(zoom-in) + 옆 패널.**
   지금(`/islands/:id`로 완전히 다른 페이지로 이동)은 "지도 같은
   느낌"이 안 산다는 게 이유 - 지도가 화면에서 사라지지 않고
   계속 유지된 채로, 클릭한 섬 쪽으로 확대되고 Topic/스크랩
   목록이 옆에 패널로 뜨는 게 목표.
3. **스크랩 추가는 온디맨드 패널.** "+" 같은 버튼으로 열고 닫는
   패널(URL/userContext/추천 Topic).
4. **데스크톱/모바일이 같은 구조를 공유**, 기본 노출 여부만 다름:
   - PC: 보조 패널(Island 목록, 최근 스크랩 등)이 상시 노출돼도
     괜찮음(공간 여유).
   - 모바일: 기본적으로 접혀 있다가 필요할 때 펴는 쪽으로
     (사용자 본인 의견, GPT 제안보다 우선 반영).
   - 즉 레이아웃을 두 벌 만드는 게 아니라, 같은 컴포넌트의
     기본 열림/닫힘 상태만 반응형으로 바뀐다.

## 패널(Panel) 구조 확정 (이어진 논의, 같은 날)

줌 애니메이션 구현 방식보다 "패널이 사용자가 뭘 할 수 있는지를
결정하는 UX 구조"이므로 패널 종류부터 확정하는 게 먼저라는 데
합의(줌은 패널이 정해지면 자연스럽게 따라오는 구현 디테일).

**패널 4종**:

1. **Island 패널** - 지도에서 섬 클릭 시 열림(동시에 카메라가 그
   섬으로 이동). Topic 목록, 스크랩 목록, 통계(Cosine Variance/
   Override Rate)를 담음 - 지금 `IslandDetailPage.tsx`의 내용을
   그대로 옮기는 것에 가까움.
2. **스크랩 추가 패널** - 우측 하단 "+" 버튼으로 열림. URL/
   userContext 입력, AI 추천, Topic 선택.
3. **검색 패널** - 지도에서 바로 여는 독립 패널. **완전히 새로
   만드는 게 아니라 PR #101에서 만든 검색(Island 상세 내 Topic/
   스크랩 검색, 홈 사이드바 "최근 Scraps" 검색)을 일반화**한 것 -
   지금은 두 군데 흩어져 있는 검색을 "지금 어느 섬에 있는지 몰라도
   전체에서 찾기"가 가능한 하나의 전역 패널로 승격.
4. **알림/작업 패널(나중, 지금은 설계만)** - Mechanism Topic 후보,
   Extraction 경고(WARN 로그 등) 같은 것들이 들어갈 자리. 지금은
   범위 밖 - 존재할 자리만 미리 마련.

**패널의 동작 규칙(공통)**:
- 여러 패널이 **상태(state)로는 동시에 열려 있을 수 있음**
  (Island 패널을 열어둔 채로 스크랩 추가 패널도 열 수 있음 -
  배타적으로 막지 않음).
- 다만 **화면에 몇 개를 동시에 그리는지는 뷰포트에 따라 다름**:
  데스크톱은 여러 패널을 독립적인 작은 "창(Window)"처럼 동시에
  띄움(겹치지 않게 배치), 모바일은 한 번에 하나만 Bottom Sheet로
  보여주고 나머지는 뒤에 쌓아둠(닫으면 이전 패널이 드러나는 스택
  구조). 상태 모델은 하나, 렌더링만 반응형으로 다르다는 원칙(앞서
  합의한 사이드바 기본 열림/닫힘 원칙과 동일한 패턴 재사용).

**컴포넌트 구조**: `Map`은 절대 언마운트되지 않고, 내부적으로
`Camera`(줌/팬 상태) + `Islands`(지도 위 섬 렌더링) + `OverlayPanel`
(위 4종 패널을 여닫는 레이어)로 구성. URL은 `/islands/3`처럼
계속 바뀌어도(공유 가능하게) 실제 렌더링에서는 `Map`이 그대로
있고 `OverlayPanel` 상태만 바뀜 - "새 페이지"가 아니라 "새 창 하나
추가"가 기능 확장의 기본 단위가 된다는 게 이 구조의 핵심 이점(패널을
"창"처럼 취급하는 프레이밍).

**"창(Window)" 프레이밍의 장점**: 앞으로 기능이 늘어나도 새 페이지를
만드는 대신 새 패널 하나만 추가하면 됨 - 사용자는 항상 같은 세계
안에 있고, 필요한 정보만 창으로 꺼내 보는 느낌을 유지("탐험" 중심
철학과 일치).

## 기술적 함의 (아직 구현 안 됨, 다음에 다룰 것)

이번 재설계는 지금까지 해온 "기존 기능에 작은 개선 얹기"(PR
#101/#102)와는 무게가 다르다 - 실질적인 재설계+재구현:

1. **라우팅 구조 변경 필요** - 지금은 섬 클릭 시
   `IslandDetailPage`가 `MapView`를 완전히 대체(언마운트)한다.
   Map-as-home 구조에서는 URL은 `/islands/:id`로 바뀌어도(공유
   가능하게 유지) 실제로는 `MapView`가 계속 마운트된 채로 옆에
   패널만 열리는 구조여야 한다.
2. **실제 확대/축소(zoom/pan) 애니메이션 필요** - 지금
   `MapView.tsx`는 고정 `viewBox`에 원을 배치만 하는 정적 SVG.
   "섬 쪽으로 카메라가 줌인"하는 느낌을 내려면 transform 기반
   애니메이션이 새로 필요함(현재 없음).
3. **Topic/스크랩 목록을 페이지가 아니라 옆 패널 컴포넌트로
   재구성** - 지금 `IslandDetailPage.tsx`의 내용(TopicCandidates/
   TopicMapView/TopicList/ScrapList)을 패널 안에서 쓸 수 있는
   형태로 다시 짜야 함.
4. Island 좌표 자체가 지금은 실좌표가 아니라 index 기반 원형
   배치(wireframe, PR #95 커밋 메시지에도 명시)라 - 진짜 좌표
   설계(`docs/vision.md`가 그리던 "새 섬은 Nearest Neighbor로
   로컬 배치, 기존 섬은 안 움직임")도 이 재설계와 맞물려서 다시
   다뤄야 함.

## Island 좌표 아키텍처 (확정, 2026-08-03)

"주제에 따라 갈리게 할지, 생성 순서로 할지"를 논의하다가 확정된
구조. 핵심 문제의식: 지금 8개 섬을 생성 순서 기반으로 영구 저장해버리면
의미 없는 값이 그대로 굳어버리고, 몇 달 뒤 AI/LLM/MCP 같은 새 섬이
생겨도 계속 엉뚱한 위치에 흩어짐 - "AI랑 바이오가 왜 반대편이지?"
같은 위화감이 영구적으로 남는다.

**세 가지 원칙**:
1. `Island`는 `x`, `y`를 영구적으로 가질 수 있지만, **초기에는
   NULL을 허용**한다 - 아직 확정 안 된 상태를 정직하게 표현.
2. **좌표 계산 책임은 `MapCoordinateService`(백엔드 Spring 서비스)
   하나로 집중**한다 - 이 프로젝트가 계속 지켜온 "결정 로직은
   백엔드"(`CosineSimilarity`/`IslandRecallService`/
   `ExtractionQualityEvaluator`와 같은 패턴) 원칙 그대로. `GET
   /islands`류 API 응답은 **항상 x,y가 채워진 채로** 내려감(DB가
   NULL이어도 서비스가 임시 좌표를 계산해서 채움) - 프론트엔드는
   폴백 로직을 따로 구현하지 않고 API가 준 값을 그대로 그리기만
   하면 된다. MapView/줌 카메라/미니맵/검색 결과 이동/"이 섬으로
   이동" 등 좌표가 필요한 모든 곳은 전부 이 서비스(또는 이 서비스가
   채워준 API 응답)만 거친다 - 어떻게 계산됐는지(DB 값인지 임시
   값인지, 나중에 캐시를 쓰는지)는 완전히 숨겨진다.
3. **Nearest Neighbor가 준비되기 전까지는 임시 좌표(원형 공식)를
   매번 계산해서 보여주고, 준비되는 순간 NULL인 좌표를 한 번만
   영구 계산해서 DB에 저장**한다 - 임시 좌표를 영원히 쓰는 게
   아니라, 최종 알고리즘이 준비되는 순간 한 번만 확정.

**좌표 생명주기(Lifecycle)**:

```
Island 생성
  │
  ▼
x, y = NULL

  │
  ▼
MapCoordinateService가 좌표 요청을 받음
  │
  ├─ DB에 좌표가 있나? YES → 그대로 사용
  │
  └─ NO → 임시 좌표 계산(원형 공식, 저장 안 함)
  │
  ▼
화면에 표시


[Nearest Neighbor 준비되는 시점]
  │
  ▼
Migration 실행
  │
  ▼
x, y가 NULL인 모든 Island
  │
  ▼
Nearest Neighbor로 좌표 계산
  │
  ▼
DB에 저장
  │
  ▼
이후 영구 사용(이 섬은 다시 안 움직임)
  │
  ▼
이후 새로 생성되는 Island도 같은 알고리즘(NN)으로 즉시 계산
```

**이 구조의 이점**: 지금 있는 8개 섬도 NN이 완성되는 날 한 번만
계산해서 DB에 저장하면 끝 - 그 이후엔 안 움직인다. "임시 좌표를
영원히 쓰는 것"과 "의미 없는 생성 순서가 영구 좌표가 되는 것"을
동시에 피한다. 줌/카메라 등 좌표 소비 쪽 코드는 "좌표를 어떻게
구했는지" 전혀 몰라도 되므로, 나중에 임시 공식 → NN으로 알고리즘이
바뀌어도 UI 쪽 재작업이 필요 없다.

### 좌표는 임베딩 압축이 아니라 "세계에서의 위치"다

"1536차원 embedding을 2차원으로 어떻게 압축하나?"라는 질문에서
출발했는데, **압축은 하지 않는 게 맞다는 결론**. PCA/t-SNE/UMAP
같은 차원축소 기법은 새 데이터가 추가될 때마다 전체를 다시 계산하며
기존 점들의 위치까지 같이 흔든다(특히 t-SNE/UMAP은 데이터 하나만
늘어도 레이아웃 전체가 크게 바뀌는 것으로 알려짐) - "기존 섬은
절대 안 움직인다"는 원칙과 정면으로 충돌.

대신 하는 일은 **압축이 아니라 탐색 + 오프셋**:

```
새 Island 생성
  │
  ▼
1536차원 embedding 생성(기존과 동일)
  │
  ▼
기존 Island들과 cosine similarity 계산(CosineSimilarity.findTopK 재사용)
  │
  ▼
가장 가까운 Island 선택(고차원 그대로, 압축 없음)
  │
  ▼
그 Island의 이미 저장된 (x,y) 주변 후보 오프셋 탐색
  예: (100,0) (-100,0) (0,100) (0,-100) (70,70) ...
  │
  ▼
기존 섬과 안 겹치는 위치를 새 Island의 (x,y)로 확정
```

이 계산은 **새로 생성되는 Island 하나의 좌표만** 정한다 - 기존
Island들의 좌표는 전혀 재계산하지 않는다.

### 좌표 범위와 단위

- **범위 제한 없음** - `double x`, `double y`로 충분. 1000이든
  100000이든 상관없다. 화면에는 카메라가 보여주는 영역만 그려진다
  (게임 엔진의 월드 좌표와 같은 방식). `docs/vision.md`의 "세계는
  완성되지 않는다" 원칙과도 맞음 - 좌표에 인위적 상한을 두지 않는다.
- **좌표는 화면 픽셀이 아니라 World Unit** - DB/서비스가 다루는
  (x,y)는 항상 월드 좌표고, 화면에 그릴 때만
  `screenX = worldX * zoom + cameraOffsetX`(y도 동일)로 변환한다.
  이렇게 분리해두면 줌/팬이 바뀌어도 DB의 좌표는 전혀 안 건드리고
  화면 그리기만 다시 하면 된다 - 렌더러가 SVG에서 Canvas/PixiJS로
  바뀌어도 월드 좌표 체계는 그대로 유지됨. `MapCoordinateService`는
  월드 좌표만 책임지고, "화면에 어떻게 그릴지"(카메라/줌/팬)는
  프론트엔드 쪽 별개 레이어의 책임.
- 월드 유닛의 구체적 크기(예: "100 = 섬 하나 간격")는 지금 미리
  못박지 않는다 - 실제로 렌더러로 그려보면서 조정하는 게 이
  프로젝트의 기존 습관(숫자는 실제로 보기 전에 확정 안 함)과
  맞음. "일관된 단위 개념이 존재한다"는 것만 지금 정해둔다.

### 내일 구현 시작점 (확정) - 2026-08-04에 전부 구현 완료(PR #103)

1. `Island`에 `x`, `y` 컬럼 추가(초기 NULL 허용). ✅
2. 좌표는 화면 좌표가 아니라 World Unit으로 정의(위 내용). ✅
3. `MapCoordinateService`를 좌표를 제공하는 단일 진입점으로 두고,
   UI(MapView/줌 카메라/미니맵/검색 결과 이동 등)는 항상 이
   서비스(또는 이 서비스가 채운 API 응답)를 통해서만 좌표를 쓴다. ✅

## Nearest Neighbor 배치 알고리즘 (설계 확정, 2026-08-05, 구현 전)

`MapCoordinateService`의 임시 원형 배치를 대체할 실제 배치 규칙.
구현 예정 진입점 이름: `NearestNeighborCoordinateStrategy`(가칭).

### 먼저 정리한 근본 제약 - 세 가지를 동시에 가질 수 없다

| 원하는 성질 | 전역 투영(PCA/t-SNE/UMAP) | 지금 채택한 방식(로컬 anchor) |
|---|---|---|
| 모든 의미적 거리를 정확히 보존 | △(근사만 가능, 2차원 자체의 수학적 한계 - 예: 서로 등거리인 점 4개는 2차원에 못 담고 3차원이 필요) | ❌ |
| 기존 섬이 절대 안 움직임 | ❌(새 데이터 추가마다 전체 재배치) | ✅ |
| 입력 순서와 무관하게 항상 같은 배치 | ✅ | ❌(순서 의존적) |

세 성질을 동시에 만족하는 방법은 없다 - 수학적 한계(2차원에 고차원
관계를 완전히 담을 수 없음)와 설계 원칙(기존 섬 안 움직임) 둘 다에서
비롯된 제약. World Engine은 "논문용 시각화"가 아니라 "사용자가
공간 기억을 쌓아가는 세계"이므로, 안정성(둘째 행)을 지키고
순서 의존성(셋째 행)을 감수하는 쪽을 명시적으로 선택한다. 순서가
달라지면 최종 지도 모양도 달라질 수 있다는 것을 알고 가는 결정.

### 최종 알고리즘 (4단계)

```
새 Island 생성
  │
  ▼
1. 기존 Island 중 cosine similarity Top-1 선택 (Anchor)
   - CosineSimilarity.findTopK 재사용, 압축 아님(고차원 그대로 비교)
  │
  ▼
2. similarity → 목표 반경(distance) 계산 (아래 수식)
  │
  ▼
3. Anchor 기준 후보 위치 생성(그 반경에서 각도 탐색)
  │
  ▼
4. 충돌 검사(다른 Island와 최소 거리 이상인지)
   - 통과 → x,y 저장
   - 실패 → 반경을 조금 늘려서 3번부터 재시도
```

방향(direction)은 Anchor가, 거리(radius)는 similarity가, 실제
빈자리(angle)는 충돌 회피가 정한다 - 세 요소가 역할을 나눈다.

**Top-1만 쓰는 이유**: 구현이 단순하고, "왜 이 위치인지" 설명하기
쉽고, 디버깅이 쉽다. Top-3 가중 평균 등으로 확장 가능한 구조지만
지금은 근거 없이 안 만든다(이 프로젝트 반복 원칙) - 나중에 Top-1만으론
부족하다는 증거가 쌓이면 그때 확장.

### 거리 공식 - 하드코딩 표 대신 연속 함수

similarity가 대부분 0.75~0.95 사이에 몰릴 것으로 예상되어 단순
선형 매핑은 구간별 차이가 잘 안 남 - 비선형(제곱) 함수로 해결:

```
distance = MIN_DISTANCE + (MAX_DISTANCE - MIN_DISTANCE)
           × clamp((HIGH - similarity) / (HIGH - LOW), 0, 1) ^ k
```

`HIGH`(이 이상이면 MIN_DISTANCE로 clamp) / `LOW`(이 이하면
MAX_DISTANCE로 clamp) / `MIN_DISTANCE` / `MAX_DISTANCE` / 곡률 `k`
5개 상수만 조정하면 지도의 느낌(군집이 얼마나 촘촘한지)을 바꿀 수
있다. 초기값 후보: `HIGH=0.95, LOW=0.75, MIN_DISTANCE=120,
MAX_DISTANCE=450, k=2` - 어제 정한 렌더링 상수(`MAX_CIRCLE_RADIUS=
50`)에서 역산한 `MIN_DISTANCE=150`과 비슷한 자릿수. **정확한 값은
실제 렌더러로 그려보며 조정** - 이 프로젝트의 "숫자는 실제로 보기
전에 확정 안 함" 습관 그대로 유지.

**남는 한계**: similarity가 비슷한 섬이 여러 개면(예: AI/LLM/RAG가
전부 0.95) 전부 같은 반경을 원해서 결국 각도 탐색(3~4단계)에만
의존하게 된다 - 이건 의도된 근사의 한계이지 버그가 아니다. 또
anchor 주변이 이미 붐비면 충돌 회피 때문에 반경이 similarity가
암시하는 것보다 훨씬 커질 수 있음 - "거리가 similarity를 대략
반영하지만 항상 정확하진 않다"는 근사로 받아들인다.

### 아직 안 정한 것 (구현 시 결정)

- 3단계 후보 위치 생성 방식: 고정 각도(8/16방향) 링 확장 vs 나선
  (spiral) 탐색 - 둘 다 검토했고 결과 구조에 영향 없음(둘 중 뭘
  써도 위 4단계 알고리즘은 동일), 구현하면서 선택.
### 마이그레이션 설계 (확정, 2026-08-05)

기존 8개 Island는 전부 NULL이라 "생성 이벤트"에 못 얹는다 - 별도의
**한 번짜리 일괄 처리**가 필요. 실시간 생성(앞으로 새로 생기는
Island)과 이 일괄 처리가 같은 알고리즘을 재사용하도록 설계한다.

**핵심 인터페이스** - `NearestNeighborCoordinateStrategy`는 JPA
엔티티에 안 묶인 순수 함수로 둔다:

```
Coordinate calculate(Embedding embedding, List<PlacedIsland> placed)
```

`PlacedIsland`는 `(x, y, embedding)` 튜플. 신규 Island 생성
(`ScrapConfirmService.resolveIsland()`)과 마이그레이션 둘 다 이
함수 하나만 호출한다.

**`CoordinateMigrationService`는 영구 코드로 남긴다** - "한 번 쓰고
버릴 스크립트"가 아니라, 실시간 생성과 동일한 로직을 여러 Island에
대해 반복 호출하는 것뿐이라 원래부터 재사용 가치가 있다(예: 나중에
어떤 이유로 좌표가 NULL로 리셋된 Island가 생겨도 이 서비스로 다시
채울 수 있음).

```
CoordinateMigrationService.migrateAll(dryRun: boolean)
  │
  ▼
IslandRepository.findAllByOrderById()
  │
  ▼
placed = 이미 x,y가 있는 Island들(NULL 아닌 것)로 초기화
  │
  ▼
NULL인 Island를 id 순으로:
  - placed가 비어있으면 (0,0)
  - 아니면 calculate(embedding, placed)로 좌표 계산
  - dryRun=false면 DB에 저장, true면 로그만 남김
  - placed에 추가(다음 Island의 비교 대상이 됨)
```

**Dry Run 모드 포함** - 저장 없이 계산 결과만 로그로 확인하는 옵션.
내일 MIN_DISTANCE/MAX_DISTANCE/k 상수를 튜닝할 때, 매번 DB에 쓰고
MapView를 열어보는 것보다 좌표만 빠르게 반복 계산해서 눈으로
스캔하는 게 훨씬 빠르다. 실사용에 들어가기 전(지금 8개는 아직
"리허설" 단계)까지는 결과가 이상하면 그냥 재실행해도 된다는 유보도
동일하게 적용.

**실제로 한 번 실행하는 방법**: `CoordinateMigrationService`는
영구 코드로 남기되, 이걸 실제로 "한 번 호출"하는 트리거는 이
프로젝트가 계속 써온 패턴 그대로 - 임시 `@Tag("live")` JUnit
테스트를 만들어 `migrateAll(dryRun=false)`를 부르고,
`./gradlew liveTest`로 실행 후 결과(로그/DB/MapView) 확인, 테스트
파일은 삭제. `CommandLineRunner`(실행 타이밍 제어가 애매함)나 임시
Controller(API를 만들고 또 지워야 함)보다 이 프로젝트에 이미 있는
패턴이 더 간단함.
