# V1 Retrospective (Genesis)

> V0가 `research_phase_1_summary.md`/`research_phase_2_summary.md`로
> 끝났듯, V1도 여기서 한 문서로 공식 종료한다. PR 단위 상세 기록은
> `experiments/v0_validation.md`에 이미 누적돼 있다 - 이 문서는 그걸
> 다시 나열하지 않고, "무엇을 검증했고 다음 질문이 뭔지"만 요약한다.

## V1의 질문

V0의 결론(Finding P2-002/P2-003: 완전 자동 분류는 현재 기술로 불가능)을
이어받아, V1이 실제로 검증하려던 질문은 하나였다.

> **"스크랩 → AI 추천 → 사용자 확인" 구조가 실제로 쓸 만한가?**

## 무엇을 검증했는가

- Content Extraction 5개 전략(Article/NaverBlog/Github/YouTube/PDF)이
  실제 사용자 URL(Round 1, N=25)에서 **88% 성공률**로 동작함
  (`docs/extraction_validation.md`).
- Two-stage 추천(Cosine Recall → LLM Pairwise Judge, Neutral objective)이
  실제로 순위를 뒤집는 걸 확인(PR #62) - Cosine 1위를 LLM이 재정렬.
- Scrap Flow 7단계(추출→임베딩→추천→확인→Island 배정)가 실제 URL로
  끝까지 완주(PR #64, 이 프로젝트 첫 `main` 머지).
- 조회 API, 정정 기록(`wasCorrected`), 미확정 스크랩 재방문 흐름,
  `/scraps/stats`까지 붙여서 최소 UI로 실제 클릭 가능한 제품이 됨
  (PR #65~71).

## 무엇이 성공했는가

- **추천은 "자동 확정"이 아니라 "후보 제시"로 충분히 동작한다.**
  Two-stage 구조가 실제로 관련 있는 Island를 상위 후보로 올리고,
  최종 판단은 사용자가 클릭 한 번으로 내리는 흐름이 실사용에서
  막히지 않았다(PR #67~70에서 반복 확인).
- 봇 차단(로봇 배제)과 JS 렌더링은 서로 다른 문제라는 V0/V1 초기
  가설이 실사용으로 재확인됨 - 네이버 블로그는 가벼운 2단계 요청으로
  해결(PR #51), 반면 대형 오픈마켓은 우회 시도 없이 Known Limitation으로
  남김(PR #72).
- 문제가 실제로 발견될 때마다 "증거 없이는 안 만든다" 원칙을 지키며
  좁게 고쳤다 - PDF NUL 바이트(PR #73), 이커머스 보일러플레이트
  감지(PR #75) 모두 새 인프라 없이 기존 컴포넌트 확장으로 해결.

## 무엇이 아직 해결되지 않았는가 (Findings)

실사용 중 코드 수정 없이 기록만 해둔 관찰들 - V2가 풀어야 할 재료.

- **Finding V1-001**: 이커머스 페이지는 배송/반품 같은 boilerplate가
  관심사 신호보다 강하게 나타날 수 있다. 텍스트 밀도 체크로 완화했지만
  (PR #75), 근본적으로 "이 URL이 커머스인가"를 사전에 판별하는 문제는
  여전히 안 풀림 - 지금은 도메인 무관하게 텍스트만 보는 방식으로 우회.
- **Finding V1-002**: JS 렌더링에 의존하는 SPA(예: `zero-base.co.kr`)는
  추출 자체가 안 되는 도메인이 존재한다. `ExtractionQualityEvaluator`로
  "실패를 정직하게 실패로 처리"하는 데까지는 갔지만(PR #69), Round 1
  KPI에 영향이 없을 만큼 드문 사례라 Playwright 같은 헤드리스 브라우저
  도입 근거는 아직 없음.
- **Finding V1-003**: 같은 Island 안에서도 대표 스크랩 간 유사도 편차가
  크게 나타난다(예: "여행" Island 내부에서 관광 코스형 vs 맛집
  리스트형 콘텐츠가 섞이며 0.25~0.75 편차, PR #72 실사용 회귀 세션).
  버그가 아니라 **하나의 Island 안에서 주제가 갈라지기 시작했다는
  신호**로 해석했다.
- **Finding V1-004(운영/측정)**: 추천 수락률(`/scraps/stats`)은 V1이
  QA/디버깅 목적으로 다양한 카테고리를 의도적으로 흩뿌려 테스트한
  데이터 위에서 계산된 값이라, 실제 사용자 경험을 반영하는 지표가
  아니다. 측정 목적과 사용 패턴이 안 맞아서 V2 Go/No-Go 기준에서
  제외한다 - 대신 이 문서의 정성적 Finding들을 근거로 쓴다.

## V2에서 풀 질문

V0(자동 분류가 가능한가) → V1(추천+확인 구조가 되는가)에 이어, V2는
새 기능 목록이 아니라 새 질문이어야 한다. Finding V1-003이 가장
직접적인 단서를 준다.

> **관심사는 언제, 어떻게 분화되어야 하는가?**
> (Island 내부에서 Topic이 갈라지는 시점 - 성장 지표/시각적 티어
> `Seed → Islet → Village → City`와 함께, `README.md` Roadmap에
> 이미 "V2 — Evolution (성장 지표, 시각적 티어, Topic 분화)"로
> 예정돼 있던 방향과 일치)

Finding V1-001(이커머스 라우팅 문제)과 V1-002(JS SPA)는 아직 실사용
빈도가 낮아 V2의 핵심 질문으로 승격하지 않고, 계속 "증거가 쌓이면
재검토"로 남겨둔다.
