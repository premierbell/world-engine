# V2 Architecture Review — Topic 후보 생성/매칭

> 이 문서는 새 Finding을 만드는 문서가 아니다. `experiments/v0_validation.md`에
> 흩어져 있는 실험/Finding들을 Stage 단위로 한 번 모아서, "이미 검증된 부분"과
> "알고 있지만 아직 안 고친 부분"을 구분하기 위한 정리 문서다. V0의
> `research_phase_1_summary.md`/`research_phase_2_summary.md`가 했던 역할을
> V2 Topic 시스템에 대해 한다.

## 왜 지금 이 문서를 쓰나

V2 핵심 기능(후보 생성/기존 Topic 매칭/승인/편입/병렬화)은 전부 구현되고
실사용으로 한 번씩 검증됐다(PR #80~90). 여기서부터는 "기능을 더 만드는 단계"가
아니라 "이 구조가 오래 버틸 수 있는가"를 보는 단계로 넘어가야 한다는 판단.

**제품 개발 단계로 넘어가는 기준**(합의):
1. 알고 있는 구조적 문제가 전부 목록화되어 있다.
2. 새로운 Finding이 실사용 중 거의 안 나온다.
3. 남은 문제들이 "설계 결함"이 아니라 "개선 사항" 수준이다.

지금은 1번을 만드는 단계 - 이 문서가 그 목록이다. 2~3번은 아직 확인 중.

## Stage 1 — 기존 Topic 매칭 (`existingTopicMatches`)

새 미분류 스크랩을, 이미 있는 각 Topic의 멤버 전원과 비교해서 최고점(≥0.6)을
찾는 단계. `TopicCandidateService.generateCandidates()` 앞부분.

**장점**
- 구조적으로 Stage 2보다 관대하다 - "전원 동의"가 필요한 Clique-safe와 달리,
  멤버 중 단 하나와만 강하게 겹쳐도 매칭됨. 그래서 Finding A(granularity
  mismatch)의 영향을 상대적으로 덜 받는다.
- 실사용 검증(2026-07-30, 개발 Island): 신규 스크랩 7개 중 6개가 사용자
  의도와 정확히 일치하는 Topic으로 매칭됨(알고리즘 2/2, 개발 면접 4/5 -
  나머지 1개는 실제로 결이 다른 콘텐츠였음, 아래 참고).

**병목**
- **O(미분류 수 × Topic당 멤버 수 합계)** - Topic 하나가 아니라 그 Topic의
  멤버 전부와 비교한다. Topic이 잘 작동해서 멤버가 계속 늘어날수록(=기능이
  성공할수록) 다음 매칭 비용이 계속 커지는 구조. Stage 2의 O(n²)와 반대로
  **자연히 줄어들지 않고 무한정 커진다** - Topic이 잘 자랄수록 오히려 더
  아프다는 게 Stage 2와의 핵심 차이.

**미해결 - cosine Top-K는 기각됨, 대안은 아직 없음**
- cosine 상관관계 실험(AI Island, Pearson 0.60)은 **절대 threshold**로
  거르는 용도로는 약하다고 결론 냈다(안전 cutoff 0.38에서 19.5%만 감소).
- 이어서 "Topic 멤버가 많을 때 cosine으로 상위 K개만 추려도 되는가"를
  다른 각도로 실험 - 1차(개발 Island, N=7)에서는 7/7 전부 cosine 1등이
  Mechanism 최고점과 일치해서 유망해 보였지만, **후보 풀이 2~6개로 작고
  Topic 2개뿐이라는 표본 문제**가 있었다(사용자가 직접 지적). 후보 풀을
  21개로 늘리고 도메인을 바꿔("여행" Island 전체, Topic 경계 없이 231쌍)
  재검증한 결과 **반례 발견**: Mechanism 0.85인 실제 관련 쌍("부산광역시/
  관광" ↔ "부산 광안리 여행 코스 추천")이 cosine 순위로는 8등/21개 -
  Top-5 shortlist였어도 놓쳤을 관계. **결론: cosine Top-K를 Stage 1의
  일반적 최적화 전략으로 채택하지 않는다** (2026-07-30).
- 대신 질문 자체를 다시 볼 필요가 있음 - "Stage 1을 어떻게 빠르게
  할까"가 아니라 "Topic을 어떻게 대표할까"(멤버 전원과 비교하는 대신
  대표 스크랩 몇 개 또는 Topic 단위 표현과 비교)가 진짜 질문일 수
  있음. 다만 V0 `prototype/world.py`의 `Topic.center_vector`(평균
  임베딩 centroid)가 작은 표본에서 embedding noise에 그대로 노출돼
  실패했던 전례(Finding #005/#006)가 있어 똑같은 함정에 빠지지 않도록
  근거 없이 바로 시도하지 않는다.
- 지금 Topic들이 아직 작아서(6~10개) 당장 아프진 않음 - **검증된 대안이
  없는 채로 알고 있는 병목만 있는 상태**. Topic이 20~30개 이상으로
  커진 뒤 실제 데이터로 다시 접근.

## Stage 2 — 신규 Topic 후보 그룹 발견

Stage 1에서 안 걸린 "진짜 미분류" 스크랩들을 대상으로 전체 쌍을 Mechanism으로
채점하고 `TopicGroupingStrategy`(Clique-safe)로 묶는 단계.

**장점**
- Island 하나를 처음 부트스트랩할 때(Topic이 아직 없을 때)만 주로 필요한
  기능으로 보임 - 이후로는 Stage 1이 대부분 흡수해서 대상 풀이 자연히 준다.
- Mechanism 신호 자체는 V0 Finding #012(AUC 0.82~0.94)부터 지금까지 반복
  검증되어 신뢰할 수 있는 자산.

**병목**
- **O(n²)** - 미분류 스크랩 수의 제곱. AI Island(22개, 231쌍) 기준 병렬화
  (PARALLELISM=2) 후에도 83초. n=50이면 약 7분, n=100이면 약 25분 추정
  (실측 기반 외삽, 2026-07-30 cosine 실험 로그).
- cosine pre-filter로 줄여봤지만(같은 실험) 안전 구간에서 19.5%밖에 못
  줄임 - **도입 안 함**으로 결론.

**미해결**
- "Topic 없는 어린 Island가 갑자기 커지는" 예외 상황에서만 문제가 되는
  것으로 잠정 결론 - 실사용에서 실제로 이 상황이 반복되면 재검토.

## Grouping 전략 (Clique-safe)

Stage 2의 pairwise 점수 행렬을 실제 그룹으로 묶는 알고리즘. 신규 멤버가
그룹 전원과 threshold 이상이어야 편입되는 greedy first-fit.

**장점**
- Connected Components의 체이닝 문제(A-B, B-C 관련 있어도 A-C 무관하면
  전부 묶이는 것)를 해결 - 최소 점수 분포가 0.60~0.95로 항상 threshold
  이상(체이닝 없음)임을 실측 확인(여행 Island, 24개).

**병목/미해결**
- **Recall 손실**: greedy 처리 순서 때문에 진짜 관련 있는 항목이 그룹에서
  탈락하는 사례 확인 - "서울특별시/관광 ↔ 경복궁"(PR #85), "LangGraph
  글 2개가 서로 못 묶임"(AI Island, 2026-07-30).
- 2026-07-30 개발 CS 실험에서는 이 실패 모드가 재현 안 됨(raw score 자체가
  낮아서 애초에 묶일 관계가 아니었음) - **증거가 엇갈림, 표본 더 필요**.
  지금은 "이따금 발생하지만 빈도는 낮음" 정도로만 판단.

## Mechanism Judge (LLM Pairwise, 비교 대상)

"같은 구체적 하위 주제/대상을 다루는가"를 판단하는 프롬프트. V0
`pairwise_judge.py`의 mechanism objective를 그대로 포팅.

**장점**
- 신호 자체는 매우 좋음(V0 Finding #012, AUC 0.82~0.94) - 이 세션 내내
  반복 확인됨. "판단이 틀렸다"고 볼 만한 사례는 실제로는 거의 없었음.

**병목/미해결 (이 세션의 핵심 발견)**
- **Finding A(핵심) - Topic granularity mismatch**: Mechanism의 판단
  목적("같은 구체적 대상")과 사용자가 원하는 관리 단위("같은 관심사
  폴더")가 다르다. 개발 CS 실험에서 raw score로 직접 확인 - "면접" 내부
  15쌍 중 13쌍이 0.00~0.20(자료구조 면접 vs DB 면접 등을 정확히 다른
  대상으로 구분) - **threshold를 조정하거나 프롬프트를 고쳐서 풀 문제가
  아니다.** 대신 이미 있는 "여러 후보를 합쳐서 하나의 Topic으로"(PR #88)
  도구로 사용자가 직접 관리 단위를 재조합하는 게 현재 해법.
  - **설계 원칙으로 재해석(2026-07-30, 바이오 Island 40개 실험)**:
    "AI가 잘했다"가 아니라 **현재 시스템 제약을 고려하면 왜 이 전략이
    합리적인가**로 초점을 둔다. 근거 둘: ① 사람도 적정 Topic 크기를
    항상 일관되게 정하지 못한다 - AI Island에서는 "RAG는 하나로 묶고
    싶다"는 확신이 있었지만, 바이오 Island에서는 "바이오의약품을
    하나로 할지, 정의/종류로 나눌지" 사용자 본인도 바로 결정 못함.
    즉 "정답인 Topic 단위"가 고정적으로 존재하지 않는다. ② 실제
    코드 확인 결과 `TopicController`는 생성(create)/추가(addScraps,
    merge 방향)만 있고 **Topic에서 스크랩 제거나 Topic 분할(split
    방향)은 API 자체가 없다** - 처음부터 크게 묶으면 나중에 되돌릴
    방법이 없지만, 작게 제안해두면 사용자가 "이 후보 추가"로 언제든
    합칠 수 있다(PR #88, 이미 검증됨). 이 둘을 합치면: **AI는
    "최종 Topic"이 아니라 "merge 가능한 최소 단위"를 제안하는
    역할**로 보는 게 맞다 - 하나의 진짜 주제를 여러 개의 작은 후보로
    쪼개는 것 자체는 되돌릴 수 있어 안전하지만, **서로 다른 주제를
    하나로 잘못 묶는 것(Finding C류 오매칭)은 여전히 줄여야 할 문제로
    남는다** - 이 둘을 같은 것으로 취급하지 않는다.
- **Finding C(재정의) - Context-blind similarity**: 문서 내용은 실제로
  겹치는데(할루시네이션 아님) 사용자가 신경 쓰는 축(자료 유형, 저장 목적)은
  안 본다. 예: Spring 공식 repo ↔ Spring 면접 준비 글(0.90, 실제로 Spring/
  Java 어휘가 많이 겹침). **미사용 레버**: `Scrap.userContext`("왜
  저장했나요?" 선택 입력)가 스키마에 있는데 Mechanism 비교 텍스트에
  전혀 안 쓰임 - 다음에 이 Finding을 풀 때 새 인프라 없이 시도해볼 수
  있는 첫 후보.
- **Finding D(신규, 2026-08-07) - 지역 단위는 Mechanism 판별 범위 밖**:
  실사용(여행 Island, 23개)에서 경주 관련 스크랩 8개(경주월드/석굴암/
  불국사/황룡사/첨성대/동궁과 월지/대릉원/양동마을)가 Topic 후보
  생성에서 단 하나도 서로 안 묶임을 발견 - raw score를 직접 뽑아
  28쌍 전부 확인한 결과 **26/28쌍이 정확히 0.00**, 나머지 2쌍(불국사↔
  석굴암 0.30, 동궁과 월지↔대릉원 0.20)도 threshold(0.6)에 한참
  못 미침. 애매한 쌍이 그룹핑 알고리즘에서 탈락한 게 아니라 **Mechanism
  판단 자체가 이 쌍들을 대부분 완전히 무관하다고 봄** - Finding A(같은
  관심사 안에서도 세부 대상이 다르면 구분)의 더 강한 버전으로, "같은
  도시/지역"이라는 꽤 넓은 공통점조차 판별 기준에 거의 안 잡힌다. 같은
  실험에서 제주(우도/천지연폭포)·부산(태종대/자갈치시장/용두산공원)에
  추가한 스크랩도 전부 기존 제주/부산 후보에 안 붙고 미분류로 남아
  같은 패턴 재확인(표본: 새로 추가한 8개 전부 미분류).
  - **해법 판단**: threshold를 낮추는 건 Finding A에서 이미 기각된
    접근이고(다른 Island에서 오매칭 위험만 커짐 - 이번 경우도 26/28이
    정확히 0.00이라 threshold를 어디로 낮춰도 대부분 여전히 안 묶임),
    다른 objective 프롬프트나 지리 정보 활용은 Adaptive Resolution
    영역(V1/V2 모두 명시적으로 범위 밖)이라 지금 건드릴 근거가 없다.
    **이 케이스에 맞는 해법은 이미 시스템에 있다** - 사용자가 체크박스로
    8개를 직접 선택해서 "선택한 스크랩으로 Topic 생성"으로 수동으로
    "경주" Topic을 만드는 것. Design Principle("AI는 Topic의 가능성을
    보여주고, 사용자가 Topic을 만든다")이 정확히 이런 경우를 위한 것 -
    AI가 못 찾은 게 버그가 아니라, 자신 없는 건 제안하지 않고 사용자
    판단에 맡기도록 설계대로 동작한 것. 다만 "지역 단위 Topic"이 다른
    Island에서도 반복해서 필요해지는 근거가 쌓이면, 그건 Adaptive
    Resolution 논의를 다시 열 근거가 될 수 있다 - 지금은 관찰 1건뿐이라
    이르다.
  - **대조 실험(2026-08-07) - Mechanism이 원래 잘 작동해야 하는
    도메인에서 검증**: Finding D 하나만 남기면 "Mechanism Judge가
    전반적으로 잘 안 된다"고 오해할 수 있어서, 같은 방법으로 정반대
    도메인(개발 기술 스택)을 대조군으로 실험함 - 새 Island("백엔드
    기술")에 Spring/JPA/Hibernate/QueryDSL/MySQL/Redis/Kafka/Docker
    관련 스크랩 35개(기술당 3~6개)를 넣고 동일하게 Topic 후보 생성.
    결과: **35개 중 34개(97%)가 기술별로 정확하게 그룹핑**됨 - Spring
    4/4(0.82), QueryDSL 5/5(0.90), MySQL 4/4(0.83), Redis 6/6(0.86),
    Docker 5/5(0.78), Kafka 3/4(0.78). 미분류로 남은 건 Kafka 1개뿐.
    JPA/Hibernate(7개)는 미분류가 아니라 하나의 큰 그룹 대신 두 그룹
    (2+5)으로 쪼개져 나왔는데, 이는 Hibernate가 JPA 구현체라는 실제
    개념적 중첩 때문에 생긴 것으로 - 위 Clique-safe "Recall 손실"과
    같은 패턴(관련 있는데 greedy 처리 순서 때문에 하나로 못 합침)이지
    잘못된 그룹핑은 아니다.

    **해석**: Mechanism Judge는 고장난 게 아니다 - "같은 구체적
    기술"을 판별하는 원래 목적에는 매우 정확하게 작동한다(97%).
    Finding D의 실패는 Mechanism 자체의 성능 문제가 아니라, **지역이라는
    분류 축이 애초에 Mechanism objective가 표현하도록 설계되지 않은
    영역**이라는 뜻이다. 실패 사례(경주)와 성공 사례(개발 기술)를
    나란히 두면 원인이 "LLM이 못 한다"가 아니라 "objective가 다르다"는
    쪽으로 훨씬 명확하게 좁혀진다 - 이후 아키텍처를 다시 볼 때 "무엇을
    고쳐야 하는지"(Finding A/C/Clique-safe recall 손실)와 "무엇은
    Mechanism의 정상 범위 밖이라 안 건드려도 되는지"(Finding D류)를
    구분하는 근거로 쓸 것.

## 종합

| 구성요소 | 신호/기능 자체 | 복잡도 | 사용자 기대와의 정합성 |
|---|---|---|---|
| Mechanism Judge | 검증됨(좋음, 원래 목적 도메인에서 97% - 대조 실험) | - | **불일치(Finding A/C/D, 핵심)** |
| Stage 1(기존 매칭) | 검증됨(잘 작동) | **O(T×M), 무한 성장** | 대체로 일치 |
| Stage 2(신규 그룹) | 검증됨 | O(n²), 부트스트랩 국한 추정 | Finding A/D 그대로 적용 |
| Clique-safe | 체이닝 해결 | - | Recall 손실(증거 엇갈림) |

**남은 문제가 "설계 결함"인가 "개선 사항"인가**: Finding A(판단 목적
불일치)는 프롬프트/threshold로 못 고치는 근본적인 차이라는 점은
여전하지만, 바이오 Island 실험(위) 이후로는 "결함"보다 "의도된 방향"에
가깝다고 재평가함 - 하나의 주제를 여러 후보로 쪼개는 과분화는
merge 도구로 안전하게 되돌릴 수 있고(Topic 분할 API가 없어서 반대
방향은 안 됨), 그래서 "작게 제안 → 필요시 merge"가 이 시스템에서
사실상 유일하게 안전한 기본값. **Finding D도 같은 재평가 대상** -
경주 8개가 안 묶인 것도 "잘못 묶임"이 아니라 "과분화"(각자 미분류로
남음) 방향이라, merge 도구/수동 Topic 생성으로 안전하게 되돌릴 수
있다. 게다가 같은 날 대조 실험(개발 기술 스택, 97% 성공)으로 이게
Mechanism 자체의 결함이 아니라 지역이라는 objective 밖의 축이라는
것까지 확인됨 - Finding A/D는 "고쳐야 할 결함"이 아니라 "Mechanism의
적용 범위"로 문서의 결론이 더 명확해졌다. 다만 Finding C(서로 다른
주제를 하나로 잘못 묶는 것)는 이
재평가 대상이 아니다 - merge로 되돌릴 수 없는 방향의 실수라 여전히
줄여야 할 문제. 나머지(Stage 1 스케일링, Clique-safe recall 손실)는
이미 대응 방향이 보이는 개선 사항 수준.

얼마나 자주/심하게 부딪히는지 관찰. 2026-08-07에 Finding D가 나오면서
"며칠간 새 Finding 안 나옴" 카운트는 리셋됨 - 다만 이건 여행 Island가

그 자체가 나쁜 신호는 아니다. 앞으로도 새 Finding이 며칠간 안 나오면
기준 2번 충족으로 보고 제품 단계 논의 재개.
