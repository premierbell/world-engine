# Island Growth Visual — Phase 1 설계 (시작 2026-08-08)

> Growth Point/시각적 티어(Seed→Islet→Village→City) 자체는 이미 구현
> 완료(PR #111~112, `docs/vision.md` 참고) - 지금은 라벨 텍스트 +
> 원 색상 명도로만 티어를 보여주고 있고, 이 문서는 그 다음 단계인
> "섬이 실제로 마을/도시처럼 보이는" 렌더링을 설계한다.

## 방향 - "그리기"가 아니라 "조립"

섬마다 티어별로 완성된 그림 하나를 그리는 게 아니라, 작은 에셋(지형/
나무/건물/도로 등)을 여러 개 준비해두고 Island마다 그중 일부를 골라
조합한다. 같은 Village 티어라도 섬마다 다른 조합이 나오게 하는 게
목적 - 완성된 그림 방식은 티어가 같으면 전부 똑같아 보인다는 한계가
있었다.

**결정한 것 (이번 논의):**
- 조립 방식(에셋 라이브러리 + 선택), 동적 충돌 회피 배치는 아님(아래
  "왜 anchor point인가" 참고)
- 스타일은 스케치 3종 중 **1번(Minimal Landmass)** 기반 - 불규칙한
  땅 모양 + 작은 집 실루엣, 따뜻한 색 계열. 평면 채색 대신 좌상단
  광원 기준 2톤 음영 + 바닥 그림자로 확정(실물 비교 후). 테마 이름은
  `countryside`.
- Island ID 기반 deterministic 선택(아래 참고) - 좌표가 "한 번
  정해지면 안 움직인다"는 원칙과 같은 이유로, 장식도 매번 바뀌면 안
  됨
- 렌더링 교체는 각 섬 `<g>` 내부 콘텐츠(지금은 `<circle>` 하나)만
  바뀌는 것 - `MapView.tsx`의 카메라/줌/드래그/패널 로직은 전혀 안
  건드림

## 왜 anchor point인가 (동적 배치 대신)

에셋을 여러 개 겹치지 않게 배치하는 방법은 두 가지가 있었다:

1. **동적 배치** - 좌표 배치(NN 알고리즘) 때처럼 충돌 회피 계산으로
   자리를 찾는다. 무한히 다양한 배치가 가능하지만, "길은 물가로
   이어져야 한다" 같은 그럴듯함을 보장하려면 규칙이 계속 늘어나고,
   결국 anchor point와 비슷한 걸 코드로 다시 만들게 된다.
2. **Anchor point(채택)** - 지형(terrain) 에셋마다 미리 정해둔 "자리"
   몇 개를 같이 정의해두고, 티어/개수에 따라 그중 몇 개를 채울지만
   고른다. 배치 품질이 항상 보장되고 구현이 훨씬 단순하다.

**자원 소모는 결정 기준이 아니었다** - 이 규모(섬 수십 개, 섬당 장식
요소 십여 개)에서는 둘 다 브라우저에서 사실상 공짜다. 순수하게
"품질 보장 vs 다양성" 트레이드오프로 골랐다.

**나중에 바꿔도 안 버려진다** - 집/나무/길 같은 낱개 에셋 그림은
배치 방식과 완전히 무관하다. 나중에 "섬들이 너무 비슷해 보인다"는
근거가 실제로 쌓이면, 에셋은 그대로 두고 "어디에 놓을지 정하는
로직"만 동적 배치로 교체하면 된다.

## 통일된 이미지 양식

**캔버스/좌표 규칙**
- 지형(terrain) 에셋: `viewBox="0 0 180 160"` 고정, 땅 모양은
  대략 (32~154, 74~152) 범위 안에 위치(기존 스케치와 동일)
- 지형 위에 올라가는 오브젝트(나무/건물/도로 등): **바닥 접지점이
  로컬 좌표 (0,0)**이 되도록 그린다 - 배치할 때 `translate(x, y)`
  만으로 붙일 수 있고, 에셋마다 별도 오프셋 계산이 필요 없다(스케치
  Concept 1의 `house()` 함수가 이미 이 규칙을 따름).
- 크기 등급(바닥에서 위로의 높이 기준):
  - small: 12~16 유닛
  - medium: 20~26 유닛
  - large: 30~38 유닛

**색 팔레트(고정)** - 따뜻한 톤 하나로 전부 통일. 새 에셋을 만들 때
이 팔레트 밖의 색은 안 씀. 오브젝트 계열은 전부 밝은면/그림자면
쌍으로 정의한다(아래 음영 규칙과 세트):

| 용도 | 밝은면 | 그림자면 | 비고 |
|---|---|---|---|
| 지형 | `#d9c9a3` | `#8a7a54` | 테두리에도 그림자면 색을 그대로 씀 |
| 건물 | `#4a5a68` | `#34424e` | |
| 지붕 | `#b5715a` | `#8a5646` | 유일한 난색 포인트 |
| 창문/디테일 | `#e8dcc0` | - | 밝은면에만 사용 |
| 식생(잎) | `#7a9b6e` | `#5c7d52` | |
| 식생(줄기/바위) | `#6b5842` | `#9c9184`(바위 전용) | |
| 기반시설(길/부두) | `#c4b896` | `#8a7048` | |
| 바닥 그림자 | `rgba(43,38,32,0.16)` | - | 모든 오브젝트 공용 |

**음영 규칙(확정, 2026-08-08 실물 비교 후)** - 평면 채색 대신 **좌상단
광원 기준 2톤 음영**을 쓴다: 왼쪽/위를 향한 면은 밝은면, 오른쪽/
아래를 향한 면은 그림자면 색으로 나눠 그린다(지붕도 두 경사면으로
나눔). 바닥에는 공용 그림자 색(`rgba(43,38,32,0.16)`)으로 오브젝트
기준 오른쪽 아래로 살짝 치우친 옅은 타원을 깐다. 그라디언트/blur
필터는 안 씀(지도 축소 상태에서도 가볍고 선명하게 보이는 걸 우선).
**모든 에셋이 같은 방향에서 빛을 받아야 한다** - 그래야 여러 에셋을
한 섬에 같이 놓았을 때 자연스럽게 붙어 보인다(따로 만든 에셋을
조합하는 구조라서 특히 중요).

## 에셋 분류와 티어별 구성

```
terrain          (지형 - 섬 밑바탕, 항상 1개)
nature           (나무/바위 - 배경 채움)
building         (집/건물)
infrastructure   (길/부두)
decoration       (추후, 소품)
```

**티어별 개수(가안 - 실제 에셋 만들어보고 조정)**:

| 티어 | terrain | nature | building | infrastructure | decoration |
|---|---|---|---|---|---|
| Seed | 1 | 1~2 | 0 | 0 | 0 |
| Islet | 1 | 2~3 | 1 | 0 | 0 |
| Village | 1 | 3~5 | 2~3 | 1 | 0~1 |
| City | 1 | 4~6 | 4~6 | 2 | 1~2 |

카테고리 자체가 티어마다 "해금"되는 구조 - Seed/Islet에는 building이
없거나 1개뿐이고, infrastructure는 Village부터 등장. 개수만 느는 게
아니라 "어떤 종류가 있는가"도 성장에 따라 달라지게 함.

## 테마(theme) 네임스페이스

지금 스타일(불규칙한 땅 + 따뜻한 톤 + 2톤 음영)은 첫 번째 테마 -
이름은 **`countryside`**로 정한다. 지금은 이거 하나뿐이지만, 나중에
"더 좋은 아이디어가 생기면 기존 건 그대로 두고 새 테마를 고를 수
있게" 하고 싶다는 요구가 있어서, 에셋 ID에 처음부터 테마를 포함시켜
둔다 - 두 번째 테마가 생겨도 `countryside` 쪽 에셋을 하나도 안
건드리고 그 옆에 새 네임스페이스(`forest/`, `coastal` 등)만
추가하면 된다.

**ID 규칙**: `{theme}/{category}_{name}` (예: `countryside/terrain_01`,
`countryside/building_house_small_01`). Island이 어떤 테마를 쓸지는
지금은 전역 고정값(`countryside` 하나뿐)이고, 테마가 여러 개가 되면
그때 Island별로 고를지/deterministic하게 섞을지를 별도로 정한다 -
지금 미리 설계 안 함(YAGNI).

## Anchor Point 구조

지형 에셋은 그림(SVG path)과 함께, 오브젝트를 놓을 수 있는 자리
목록을 같이 정의한다:

```ts
interface TerrainAnchor {
  x: number;
  y: number;
  size: 'small' | 'medium' | 'large';
  category: 'nature' | 'building' | 'infrastructure' | 'decoration';
}

interface TerrainDefinition {
  id: string; // 'countryside/terrain_01' - {theme}/{category}_{name}
  path: string; // 땅 모양 SVG path data
  anchors: TerrainAnchor[]; // 6~10개 정도, size/category 겹치게 여유 있게 정의
}
```

자리는 실제 필요한 개수(City 기준 최대 nature 6 + building 6 +
infra 2 + decoration 2 = 16)보다 넉넉하게 정의해두고, 매번 그중
필요한 만큼만 골라서 채운다 - 자리가 부족해서 특정 티어에서 에셋이
겹치는 일이 없게.

## Deterministic 선택

Island의 장식은 `islandId`를 시드로 하는 결정론적 선택으로 정한다 -
매번 다시 계산해도 같은 섬은 항상 같은 모습이 나오고(좌표/GrowthTier와
같은 이유로 DB에 저장하지 않음), 다른 섬은 서로 다르게 나온다.

```ts
function seededRandom(seed: number): () => number {
  // mulberry32 - 작고 충분히 균일한 시드 기반 PRNG
  let t = seed;
  return () => {
    t += 0x6d2b79f5;
    let r = Math.imul(t ^ (t >>> 15), t | 1);
    r ^= r + Math.imul(r ^ (r >>> 7), r | 61);
    return ((r ^ (r >>> 14)) >>> 0) / 4294967296;
  };
}
```

`seededRandom(island.id)`로 만든 함수 하나를 그 섬의 조립 과정 내내
순서대로 소비한다(지형 선택 → 채울 anchor 고르기 → 각 자리에 들어갈
구체적 에셋 변형 고르기) - 같은 섬이면 항상 같은 순서로 같은 값이
나와서 결과가 고정된다. 렌더링(프론트, `MapView.tsx` 쪽)에서만
계산하고 백엔드는 안 건드림 - `tier`/`scrapCount`는 이미 API가 주고
있고, 장식은 순수하게 화면에 어떻게 그릴지의 문제라 새 필드가 필요
없다(`MapCoordinateService`의 "저장 안 하고 매번 계산" 패턴과 같은
이유).

## Phase 2 시작 에셋(최소 세트)

한 번에 다 안 만들고 이 정도로 시작해서 조합이 실제로 자연스러운지
먼저 확인한다(전부 `countryside/` 네임스페이스):

- `terrain_01`, `terrain_02`
- `nature_tree_01`, `nature_tree_02`, `nature_rock_01`
- `building_house_small_01`, `building_house_small_02`, `building_house_large_01`
- `infra_road_01`, `infra_dock_01`

(decoration은 Phase 2 최소 세트에서는 제외 - City 티어에서만 쓰이고
없어도 구성이 성립함)

## 지금은 안 하는 것

- **동적 배치 알고리즘** - 위 "왜 anchor point인가" 참고. 섬이 많이
  쌓였는데 실제로 반복적으로 보인다는 근거가 쌓이면 재검토.
- **AI가 Topic/섬마다 실시간으로 그림 생성** - 로딩 예측 불가능,
  같은 섬이 매번 바뀌어 보일 위험, 디자인 통일성 깨짐. 명시적으로
  기각.
- **두 번째 테마(Forest/Coastal 등) 실제 제작** - ID에 네임스페이스는
  넣어뒀지만(`countryside/...`), `countryside` 하나부터 제대로 만들고
  "이 에셋 시스템으로 충분히 자연스러운 섬이 나온다"를 확인한 다음에
  고려. Island별로 테마를 어떻게 고를지도 아직 미정.
- **Topic을 건물로 승격(B안)** - Island 외형(A안)이 만족스러워진
  뒤에 별도로. 이 문서는 A안만 다룬다.
- **정확한 티어별 개수 확정** - 위 표는 가안, 실제 에셋으로 4개 티어
  나란히 띄워보고 조정.
